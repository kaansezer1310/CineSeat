CineSeat — Teknik Rapor

Frontend ile backend'in nasıl konuştuğu, sistemin nasıl kurulduğu ve bu süreçte bulunup düzeltilen hatalar.

Bu belge ne için: kodu açmadan, sistemin nasıl çalıştığını ve nelerin neden değiştirildiğini anlamak için. Anlatılan her kod parçası projeden birebir alınmıştır; hangi dosyadan geldiği üstünde yazılıdır.

1. Sistemin şekli

CineSeat iki ayrı programdan oluşuyor. Bunlar aynı bilgisayarda çalışsalar bile birbirinden tamamen bağımsız iki süreçtir ve yalnızca ağ üzerinden, HTTP ile konuşurlar.

ParçaTeknolojiAdres (geliştirme)Görevi
FrontendReact + Vitelocalhost:5173 Tarayıcıda çalışır, ekranı çizer, kullanıcıdan girdi alır
Backend.NET 10 Web APIlocalhost:5207 İş kurallarını uygular, veritabanına yazar/okur
VeritabanıPostgreSQLlocalhost:5432 Kalıcı veri

Frontend'in veritabanıyla hiçbir teması yoktur. Tarayıcıda çalışan kod hiçbir zaman doğrudan SQL çalıştırmaz; her şey backend'in açtığı HTTP uçlarından geçer. Bu, güvenliğin temel taşıdır: tarayıcıdaki kod kullanıcının görebileceği ve değiştirebileceği bir şeydir, dolayısıyla ona güvenilmez.

2. Bağlantıyı kuran kod

"Frontend backend'e nasıl bağlanıyor" sorusunun cevabı tek bir satır değil, dört ayrı parçanın birlikte çalışması. Biri eksik olursa bağlantı kurulmaz.

2.1 Adres — nereye istek atılacağı

frontend/src/services/apiClient.js

const API_BASE_URL =
  import.meta.env.VITE_API_BASE_URL || "http://localhost:5207/api";

Bağlantının başladığı yer burasıdır. Frontend'in backend'i bulabilmesi için adresini bilmesi gerekir. Bu adres tek bir yerde tanımlanmıştır; projedeki hiçbir başka dosya localhost:5207 yazmaz.

import.meta.env.VITE_API_BASE_URL bir kaçış kapısıdır: canlıya çıkarken adres değişecektir ve o zaman kodu değil, yalnızca ortam değişkenini değiştirmek yeterli olur.

2.2 CORS — tarayıcının izin vermesi

Frontend 5173, backend 5207 portunda. Tarayıcı için bunlar farklı köken (origin) sayılır ve tarayıcı, bir sayfanın başka bir kökene istek atmasını varsayılan olarak engeller. Bu bir güvenlik önlemidir.

backend/Presentation/CineSeat.WebAPI/Program.cs

const string FrontendCorsPolicy = "FrontendCorsPolicy";
builder.Services.AddCors(options =>
{
    options.AddPolicy(FrontendCorsPolicy, policy =>
    {
        policy.WithOrigins("http://localhost:5173", "http://127.0.0.1:5173")
              .AllowAnyHeader()
              .AllowAnyMethod();
    });
});

Bu blok olmasaydı hiçbir şey çalışmazdı. Kod doğru, token doğru, veritabanı dolu olsa bile tarayıcı isteği göndermeden iptal ederdi. Backend'in "bu adresten gelen isteklere izin veriyorum" demesi şarttır.

Adres listesi sabit yazılmıştır. Vite başka bir porta düşerse (5173 doluysa 5174'e geçer) uygulama sessizce çalışmaz hale gelir — bu rapor hazırlanırken de bir kez yaşandı.

2.3 Tek giriş noktası — her isteğin geçtiği yer

Projede hiçbir bileşen doğrudan fetch çağırmaz. Her istek aşağıdaki fonksiyondan geçer:

frontend/src/services/apiClient.js

async function apiRequest(path, { method = "GET", body, headers } = {}) {
  const token = getStoredToken();

  const response = await fetch(`${API_BASE_URL}${path}`, {
    method,
    headers: {
      ...(body !== undefined ? { "Content-Type": "application/json" } : {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...headers,
    },
    body: body !== undefined ? JSON.stringify(body) : undefined,
  }).catch(() => {
    throw new ApiError(
      "Sunucuya ulaşılamıyor. Backend çalışıyor mu kontrol edin.",
      { status: 0, code: "NETWORK_ERROR" }
    );
  });

  if (!response.ok) {
    if (response.status === 401 && token && onUnauthorized) {
      onUnauthorized();
    }
    throw await toApiError(response);
  }

  if (response.status === 204) {
    return null;
  }

  return response.json();
}

Bu fonksiyon dört işi tek yerde yapar:

  • Adresi tamamlar — çağıran "/movies" yazar, buraya http://localhost:5207/api/movies olur.
  • Token'ı ekler — oturum varsa Authorization başlığı kendiliğinden eklenir. Hiçbir servis dosyası token'ın varlığını bilmez.
  • Ağ hatasını çevirir — backend kapalıysa fetch ham bir hata fırlatır; burada anlaşılır bir mesaja dönüşür.
  • 204 durumunu ayırır — silme işlemleri gövdesiz cevap döner; response.json() çağrılsa çökerdi.

Dışarıya açılan yüzey dört satırdır; tüm servisler yalnızca bunları kullanır: 

export const apiClient = {
  get:  (path)       => apiRequest(path),
  post: (path, body) => apiRequest(path, { method: "POST", body }),
  put:  (path, body) => apiRequest(path, { method: "PUT",  body }),
  del:  (path)       => apiRequest(path, { method: "DELETE" }),
};

2.4 Kimlik — token'ın hayat döngüsü

HTTP durumsuzdur: backend, arka arkaya gelen iki isteğin aynı kişiden geldiğini kendiliğinden bilmez. Bunu çözen şey her istekte taşınan imzalı bir belgedir — JWT.

Üretim (backend)

backend/Infrastructure/CineSeat.Infrastructure/Security/JwtTokenService.cs

var claims = new List<Claim>
{
    new(ClaimTypes.NameIdentifier, userId.ToString()),
    new(ClaimTypes.Name, username),
    new(ClaimTypes.Email, email),
    new(ClaimTypes.Role, roleName),
    new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
};

claims.AddRange(
    permissions.Select(p => new Claim(PermissionClaimTypes.Permission, p)));

var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_settings.Key));
var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

Token'ın içine kullanıcının kimliği, rolü ve izinlerinin tamamı yazılır. Sonra gizli anahtarla imzalanır. İmza sayesinde içerik kurcalanamaz: kullanıcı token'ı açıp okuyabilir ama değiştiremez — değiştirirse imza tutmaz.

Rol değil izin taşınıyor. "Bu kullanıcı Admin" demek yerine "bu kullanıcı movie.manage, user.manage… yapabilir" deniyor. Böylece yeni bir yetki eklendiğinde kod değil veri değişir ve kısıtlı yetkili yönetici tanımlamak mümkün olur.

Saklama (frontend)

frontend/src/context/AuthProvider.jsx

const login = async (email, password) => {
  const loggedInUser = await authService.login(email, password);
  setIsSessionExpired(false);
  setUser(loggedInUser);
  sessionStorage.setItem("cineseat_user", JSON.stringify(loggedInUser));
  return loggedInUser;

Token, kullanıcı nesnesinin içinde sessionStorage'a yazılır. localStorage değil: sekme kapanınca oturum düşsün diye.

Doğrulama (backend)

ClockSkew = TimeSpan.Zero bilinçli: varsayılan 5 dakikalık tolerans, süresi dolmuş bir token'ı 5 dakika daha geçerli sayar. Sıfırlandı.

Okuma (handler'lar)

2.6 Hata sözleşmesi

Backend her hatada aynı biçimde cevap verir; frontend de bu biçimi kendi hata sınıflarına çevirir. İki taraf arasındaki bu anlaşma, sayfaların HTTP kodlarıyla uğraşmasını gereksiz kılar.

backend/Presentation/CineSeat.WebAPI/Middleware/ExceptionHandlingMiddleware.cs

try
{
    await _next(context);
}
catch (ValidationException ex)
{
    await WriteAsync(context, StatusCodes.Status400BadRequest, new
    {
        title = "Doğrulama hatası",
        status = StatusCodes.Status400BadRequest,
        errors = ex.Errors
    });
}
catch (NotFoundException ex) { /* 404 */ }
catch (ConflictException ex) { /* 409 */ }

Bu, uygulamadaki tek try/catch. Hiçbir controller ve handler hata yakalamaz; hepsi istisna fırlatır, çeviri burada yapılır.

frontend/src/services/apiClient.js

switch (response.status) {
  case 400:
  case 422: return new ValidationError(message);
  case 401: return new ApiError(message, { status: 401, code: "UNAUTHORIZED" });
  case 403: return new ForbiddenError(message);
  case 404: return new NotFoundError(message);
  case 409: return new ConflictError(message);
  default:  return new ApiError(message, { status: response.status });
}

2.7 Oturum düştüğünde

Token'ın süresi dolduğunda kullanıcı "giriş yapmış" görünmeye devam eder ama her istek 401 döner. Bunu çözen bağ şu:

frontend/src/context/AuthProvider.jsx

useEffect(() => {
  setUnauthorizedHandler(() => {
    setIsSessionExpired(true);
    clearSession();
  });

  return () => setUnauthorizedHandler(null);
}, [clearSession]);

apiClient React'i hiç tanımaz — hook, context, router bilmez. Buna rağmen oturumun düştüğünü haber verebilir: AuthProvider açılırken kendi fonksiyonunu apiClient'a kaydeder. Bu, iki katmanı birbirine bağımlı yapmadan haberleşmelerini sağlar.

3. Bir isteğin uçtan uca yolculuğu

Yönetim panelinde "yeni film ekle" düğmesine basıldığında olanlar, sırayla:

  1. Bileşen servisi çağırır. Ekran fetch bilmez, yalnızca movieService.create(values) der.
  2. Servis komutu hazırlar. Form değerleri backend'in beklediği alan adlarına çevrilir, sonra apiClient.post("/movies", command).
  3. apiClient isteği kurar. Adres tamamlanır, token Authorization başlığına eklenir, gövde JSON'a çevrilir.
  4. Tarayıcı CORS ön kontrolü yapar. Token taşıyan bir POST, "basit istek" sayılmaz; tarayıcı önce OPTIONS gönderip izin sorar. Backend'in CORS politikası izin verirse asıl istek yola çıkar.
  5. Backend istisna sarmalayıcısına girer. Boru hattının en dışı UseExceptionHandling(). Bundan sonrası ne fırlatırsa fırlatsın, istemci tutarlı bir JSON alır.
  6. Kimlik ve yetki. UseAuthentication token'ın imzasını ve süresini doğrular, UseAuthorization movie.manage iznini arar. Yoksa handler'a hiç ulaşılmaz — 401 ya da 403.
  7. Controller komutu iletir. Controller iş kuralı içermez; komutu aracıya verir.
  8. Doğrulama davranışı devreye girer. Handler'dan önce çalışır; kurallar tutmuyorsa handler hiç çağrılmaz.
  9. Handler işi yapar. Repository üzerinden veritabanına yazar.
  10. Cevap geri döner. apiClient JSON'u çözer, servis arayüz şekline çevirir, ekran güncellenir.

Boru hattının sırası neden önemli

backend/Presentation/CineSeat.WebAPI/Program.cs

app.UseExceptionHandling();   // en dista: her seyi sarmali
// ...
app.UseCors(FrontendCorsPolicy);
app.UseAuthentication();      // once: sen kimsin
app.UseAuthorization();       // sonra: yetkin var mi
app.MapControllers();

CORS, kimlik doğrulamadan ÖNCE gelmek zorunda. Tarayıcının ön kontrol isteği (OPTIONS) hiçbir token taşımaz. CORS sonra gelseydi, bu istek kimlik doğrulamada 401 ile düşer ve tarayıcı asıl isteği hiç göndermezdi. Sonuç, hata ayıklaması zor bir "CORS hatası" olurdu.

Doğrulama davranışı

backend/Core/CineSeat.Application/Common/Behaviors/ValidationBehavior.cs

var results = await Task.WhenAll(
    _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

var failures = results.SelectMany(r => r.Errors).Where(f => f is not null).ToList();

if (failures.Count > 0)
{
    // Handler hiç çağrılmaz; middleware bunu 400'e çevirir.
    throw new ValidationException(failures);
}

return await next();

Bu sayede handler'ların içi tamamen iş kuralıdır; "bu alan boş mu", "bu sayı pozitif mi" gibi kontroller handler'lara hiç girmez.

4. Backend'in katmanları

Backend dört katmana ayrılmış. Kural şudur: bağımlılık her zaman içe doğrudur. Dış katman iç katmanı tanır, tersi olmaz.

KatmanİçindekilerNeyi tanımaz
Domain Varlıklar, enum'lar Hiçbir şeyi — en içteki katman
Application Komutlar, sorgular, handler'lar, doğrulayıcılar, repository arayüzleri Entity Framework'ü tanımaz
Persistence DbContext, repository uygulamaları, migration'lar HTTP'yi tanımaz
WebAPI Controller'lar, middleware, kurulum —

"Application EF'i tanımaz" kuralı somut bir sonuç doğurur: handler'lar ToListAsync gibi EF metotlarını çağıramaz. Bunun için bir arayüz konmuş:

backend/Infrastructure/CineSeat.Persistence/Data/EfAsyncQueryExecutor.cs

public sealed class EfAsyncQueryExecutor : IAsyncQueryExecutor
{
    public Task<List<T>> ToListAsync<T>(IQueryable<T> query, CancellationToken ct = default)
        => query.ToListAsync(ct);
    // CountAsync, AnyAsync, FirstOrDefaultAsync...
}

Bu kuralın pratik faydası rapordaki hatalardan birinde görüldü: veritabanına özgü bir hata kodunu (SQLSTATE 23505) yakalayıp anlamlı bir istisnaya çevirmek gerektiğinde, bunun nereye yazılacağı tartışmasızdı — EF'i yalnızca Persistence tanıdığı için oraya.

5. Bulunan ve düzeltilen hatalar

Aşağıdakiler bu süreçte ortaya çıkan gerçek hatalardır. Her biri ya canlı isteklerle ya da bir testle doğrulandı.

5.1 Ödemeye girer girmez sepetin temizlenmesi

Belirti: Kullanıcı ödeme sayfasına giriyor, anında sepeti boşalıyor ve sepete geri atılıyor.

Sebep:

frontend/src/hooks/useCountdown.js — düzeltmeden önce

const [seconds, setSeconds] = useState(initialSeconds);

useState kendisine verilen değeri yalnızca ilk render'da kullanır. Koltuk kilitleri asenkron alındığı için initialSeconds önce 0, kilitler gelince 600 oluyordu. Ama sayaç 0'da kalıyor, kilit gelir gelmez "süre doldu" tetikleniyordu.

Düzeltme:

const [syncedInitial, setSyncedInitial] = useState(initialSeconds);

if (initialSeconds !== syncedInitial) {
  setSyncedInitial(initialSeconds);
  setSeconds(initialSeconds);
}

Bu hatayı bir test buldu, elle deneme değil. Yalnızca gerçek akışta (asenkron kilit + sayaç birlikte) ortaya çıkıyordu.

5.2 Sayfa boyutu uyuşmazlığı — üç kez tekrarlandı

Backend sayfa başına en fazla 100 kayıt veriyor: 

RuleFor(x => x.PageSize).InclusiveBetween(1, 100);

Ön yüz ise 200, hatta 500 gönderiyordu. Sunucu 400 dönüyor, ekran sonsuza kadar "yükleniyor"da kalıyordu. Aynı hata üç ayrı yerde çıktı:

NeredeGönderilenSonuç
Sinema ve ilçe listeleri200 / 500400
Seans listesi (yönetim)200400
Film, yorum, favori, kullanıcı uçları—sınır yoktu: 999999 kabul ediliyordu

Sınıra inmek yeterli değildi. Bir sinemanın seansları 100'ü rahatlıkla aşabilir; pageSize=100 yapmak veriyi sessizce kırpardı. Çözüm, sayfaları tek tek dolaşmak oldu:

frontend/src/services/adminResource.js

export async function fetchAllPages(basePath, params = {}) {
  const query = buildQuery(params);

  // Çağıran belirli bir sayfa istediyse ona karışılmaz.
  if (query.has("pageNumber") || query.has("pageSize")) {
    const result = await request();
    return Array.isArray(result) ? result : (result?.items ?? []);
  }

  const collected = [];
  query.set("pageSize", String(MAX_PAGE_SIZE));

  for (let pageNumber = 1; pageNumber <= MAX_PAGES; pageNumber += 1) {
    query.set("pageNumber", String(pageNumber));
    const result = await request();

    if (Array.isArray(result)) return result;   // sayfalamayan uçlar

    const items = result?.items ?? [];
    collected.push(...items);

    const totalPages = Number(result?.totalPages) || 0;
    if (pageNumber >= totalPages || items.length === 0) break;
  }

  return collected;
}

MAX_PAGES üst sınırı bilinçli: sunucu tutarsız bir totalPages bildirse bile döngü kapanır. Boş sayfa kontrolü ikinci güvencedir.

Kampanya seçimi kalem bazına taşındı:

frontend/src/services/campaignService.js

export function planCampaignsPerItem(campaigns, items, user, calcItemSubtotal) {
  const lines = (items ?? []).map((item) => {
    const subtotal = calcItemSubtotal(item);
    const campaign = pickBestCampaign(campaigns, subtotal, user);

    return { item, campaign, subtotal,
             discount: calculateDiscount(campaign, subtotal) };
  });

  return {
    lines,
    discountTotal: lines.reduce((sum, line) => sum + line.discount, 0),
  };
}

Genel ders: istemci tarafındaki her uygunluk kontrolü, backend'in doğruladığı aynı birim üzerinde yapılmalı. Backend "sepet" diye bir şey bilmiyordu.

5.5 Beklenen durumların istisna sayılması

Üç ayrı hata aynı kökten geldi: normal bir sonuç, hata gibi modellenmişti. Bunun bedeli ağırdı — hata ayıklayıcı istisnada duraklayınca tüm süreç donuyor ve belirti her seferinde "sonsuz yükleniyor" oluyordu.

a) Zaten silinmiş kilidi bırakmak

Rezervasyon oluştuğunda kilit satırları aynı işlem içinde siliniyor. Ödeme sonrası temizlik yapan istemci, artık var olmayan kimlikleri bırakmaya çalışıyor ve her seferinde NotFoundException alıyordu.

Oysa DELETE idempotenttir: "bu kilit gitmiş olsun" demektir. Yoksa amaç zaten gerçekleşmiştir.

backend/.../ReleaseSeatCommandHandler.cs

// Kilit zaten yoksa amac gerceklesmis demektir, hata degil.
if (seatLock is null)
    return Unit.Value;

// Reddedilen istek de sessizce basarili doner: 404 dondurmek
// "bu kilit var ama senin degil" bilgisini sizdirirdi ve id deneyen
// biri gecerli kilitleri haritalayabilirdi. Kilide DOKUNULMUYOR.
if (seatLock.UserId != userId && !canManageShowtimes)
    return Unit.Value;

_write.HardDelete(seatLock);
await _write.SaveAsync(cancellationToken);

    // Bu her zaman gercek bir cakisma DEGIL.
    //
    // Basarisiz ekleme izleyicide "Added" olarak duruyor; bir sonraki
    // kayitta tekrar denenmesin diye cikariliyor.
    _lockWrite.Detach(newLock);

    existingLock = await _lockRead.GetSingleAsync(
        sl => sl.ShowtimeId == request.ShowtimeId && sl.SeatId == request.SeatId,
        tracking: true, cancellationToken);

    if (existingLock is null) throw;
}
// ...asagidaki devralma mantigina dusuyor

Canlı doğrulama:

  • Aynı kullanıcı, eş zamanlı 2 istek → 200 + 200, ikisi de aynı kilit numarası
  • Farklı kullanıcı, aynı koltuk → 409

Düzeltme yalnızca yarışı tolere ediyor, gerçek çakışmayı değil.

c) Benzersiz kısıt ihlalinin 500 dönmesi

Veritabanı doğru davranıp ikinci eklemeyi reddediyordu, ama DbUpdateException hiçbir yerde yakalanmadığı için kullanıcıya "Sunucu hatası" dönüyordu. Oysa bu beklenen bir durum: kayıt kapılmış.

backend/Infrastructure/CineSeat.Persistence/Repositories/WriteRepository.cs

private const string UniqueViolation = "23505";

public async Task<int> SaveAsync(CancellationToken cancellationToken = default)
{
    try
    {
        return await _context.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateException exception)
        when (exception.InnerException is PostgresException { SqlState: UniqueViolation })
    {
        throw new ConflictException(
            "Bu kayit baska bir islem tarafindan olusturulmus. Lutfen tekrar deneyin.");
    }
}

Konum bilinçli: Application katmanı EF'i tanımıyor, Persistence tanıyor. Bu düzeltme yalnızca koltuk kilidini değil, benzersiz kısıtı olan her yolu (kullanıcı adı, e-posta, tür adı, rezervasyon numarası) 500 yerine 409'a çeviriyor.

8. Tekrar eden üç kalıp

Bulunan hataların neredeyse tamamı üç kalıptan geldi. Yeni bir hata ararken önce bunlara bakmak zaman kazandırır.

1 — Aynı kuralın iki yerde tutulması

Sayfa boyutu sınırı, bilet tipi çarpanları, kampanya eşiği. Üçü de hem ön yüzde hem backend'de tanımlıydı ve üçü de zamanla ayrıştı.

Önlem: kuralın bağlayıcı olduğu tarafı yorumda açıkça yazmak ve bir testle sabitlemek. Kopya kaçınılmazsa (ön izleme için sunucuya sormak mümkün değil), hangisinin doğru olduğu belgelenmeli.

2 — İki tarafın farklı birim düşünmesi

Ön yüz "sepet" diye bir kavramla karar veriyordu; backend öyle bir şey bilmiyor, her rezervasyonu ayrı değerlendiriyordu.

Önlem: istemcideki her uygunluk kontrolünü, backend'in doğruladığı aynı birim üzerinde yapmak.

3 — Beklenen durumun istisna olarak modellenmesi

Zaten silinmiş kilidi bırakmak, kendi kilidini yenilemek, benzersiz kısıt yarışını kaybetmek. Üçü de normal akıştı ama istisna fırlatıyordu.

Önlem: istisna yazmadan önce "bu gerçekten bir hata mı, yoksa beklenen bir sonuç mu" diye sormak. Bedeli yüksek: hata ayıklayıcı istisnada duraklayınca tüm süreç donuyor ve belirti her seferinde "sonsuz yükleniyor" oluyordu — asıl sebeple hiç ilgisi olmayan bir görüntü.

Hata ayıklama notu: uygulama "sonsuz yükleniyor"da kalıyorsa, önce backend'in yanıt verip vermediğine bakın. Süreç hata ayıklayıcıda duraklamışsa hiçbir istek dönmez ve her ekran aynı şekilde takılır. Duraklama penceresindeki istisna tipi ve çağrı yığınının en alt satırı doğrudan sebebi gösterir.
